## 2. ScamNet — is this message a scam?

Three classes (safe / suspicious / scam). Trained on 5,782 synthetic messages built from documented Indian fraud patterns in all four languages; tested on **83 hand-written messages**, including scam types absent from training ("Mum, this is my new number", crypto doubling, gas-subsidy refunds) and genuine bank messages that mention an OTP.

| System | Accuracy | Macro F1 | Scam precision | Scam recall | False alarms on safe | Missed scams |
|---|---|---|---|---|---|---|
| Rule features only (logistic regression) | 78.3% | 0.787 | 0.957 | 0.629 | 3.6% | 10 |
| MuRIL only | 90.4% | 0.899 | 0.846 | 0.943 | 7.1% | 0 |
| **Blend, w = 0.7 (deployed)** | 90.4% | 0.899 | 0.846 | 0.943 | 7.1% | 0 |

**Reading the ablation.** Rules alone are the most *precise* on scams but miss many — they only know the mechanics they were written for. The transformer catches everything but raises more false alarms. The blend weight was fixed at 0.7 before testing; on this test set the blend equals the transformer, because the fine-tuned model is near-certain and 30% rule weight cannot overturn it. In practice the rules supply the **spoken reasons**, not the verdict.

Blend-weight curve, macro F1 (reported, *not* used to choose w — that would tune on the test set): 0.0: 0.787 · 0.1: 0.787 · 0.2: 0.787 · 0.3: 0.787 · 0.4: 0.841 · 0.5: 0.939 · 0.6: 0.899 · 0.7: 0.899 · 0.8: 0.899 · 0.9: 0.899 · 1.0: 0.899.

Per language (deployed): Hindi 95.5%, English 90.5%, Tamil 90.0%, Telugu 85.0%.

Strongest fitted rule signals: `remote_app` (+7.1), `pay_to_receive` (+6.4), `urgency` (+5.7), `asks_for_secret` (+5.4), `risky_domain` (+5.0).

## 3. Scheme search — "I need money for farming" → PM-KISAN

48 hand-written queries (12 per language) that describe a need without naming the scheme. Encoder: `intfloat/multilingual-e5-small` (chosen because its training languages include Tamil and Telugu).

| Method | Hit@1 | Hit@3 | Hit@1 by language |
|---|---|---|---|
| Keyword | 0.604 | 0.625 | Hindi 0.67 · English 0.83 · Tamil 0.42 · Telugu 0.50 |
| Embedding | 0.812 | 0.958 | Hindi 0.83 · English 0.92 · Tamil 0.75 · Telugu 0.75 |
| **Hybrid, keyword weight 0.01 (deployed)** | 0.875 | 0.958 | Hindi 0.92 · English 0.92 · Tamil 0.75 · Telugu 0.92 |

Eligibility itself is not learned: 20 schemes are declarative rules, and every verdict (eligible / maybe / not eligible) comes with the reason for each rule. "Maybe" means a fact is missing — the app asks for it instead of saying no.

Remaining misses (not patched with keywords, which would be tuning on the test set): "मेरे पति नहीं रहे, कोई मदद मिलेगी"; "insurance in case I die so my family is safe"; "என் மகளுக்காக சேமிக்க வேண்டும்"; "எனக்கு கூலி வேலை வேண்டும்"; "என் கணவர் இறந்துவிட்டார், உதவி கிடைக்குமா"; "నా కూతురి కోసం పొదుపు చేయాలి".

## 4. Vision — QR codes and banknotes

**QR verification** decodes with OpenCV (plain → CLAHE → adaptive threshold) and falls back to pyzbar, parses the UPI URI, checks the payee against the registry, and flags pre-filled amounts and hidden links.

**Sticker detection** on 120 synthetic shop posters, half with a fraudster's QR pasted over:

| Signal | AUC |
|---|---|
| rotation mismatch deg | 0.953 |
| edge ratio | 0.790 |
| brightness step | 0.605 |

Deployed (rotation mismatch): AUC **0.920**, detection 55.0%, false alarms 0.0%; decode rate 91.7%. Stickers pressed on within about a degree of square cannot be told from print by a photo.

_Caveat: Synthetic posters from a generator written alongside the heuristic. Necessary evidence, not sufficient: real shop photos are needed for a field number._

**NoteNet** is not trained: it needs 60–100 photographs of real notes per denomination, which have to be taken by hand (`ml/train_notes.py` documents the layout and is ready to run). Until then the API answers with a colour heuristic, caps its confidence at 60%, says so in the response (`backend: colour_heuristic`), and the UI tells the user to check the note themselves.
